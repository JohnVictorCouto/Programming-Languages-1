1) 
O projeto implementa uma arquitetura Cliente-Servidor multithread com comunicação bidirecional.   Servidor (ServidorBatepapo.java): Atua como o nó central. Ele aguarda conexões de clientes usando o método bloqueante accept(). Para cada novo cliente que se conecta, o servidor cria e inicia uma nova Thread exclusiva para lidar com ele. Isso impede que a aplicação trave enquanto aguarda a leitura de mensagens (com readLine()) de um cliente específico. Quando o servidor recebe uma mensagem, ele itera sobre a lista de clientes conectados e a retransmite (broadcast) para todos, exceto para o remetente original.Cliente (ClienteBatepapo.java): Conecta-se ao IP e porta do servidor. Ele também utiliza Multithreading, executando o recebimento de mensagens do servidor em uma Thread separada (run()) enquanto o fluxo principal (messageLoop()) fica bloqueado aguardando o usuário digitar mensagens no console.
Aqui está o detalhamento do que ocorreu nos bastidores dessa execução:

Servidor (Porta 3307): Foi iniciado e aceitou conexões de dois clientes diferentes, atribuindo-lhes portas dinâmicas (65017 e 53999). O servidor criou uma thread independente para cada um, recebendo as mensagens ("oi") e fazendo o broadcast (repassando) para os demais conectados.

Cliente 1 (65017): Conectou-se ao servidor, enviou a mensagem "oi" (que foi repassada ao Cliente 2), recebeu a resposta do outro cliente e, em seguida, utilizou o comando "sair" para encerrar sua execução localmente.

Cliente 2 (53999): Conectou-se, recebeu o "oi" do primeiro cliente, respondeu com o seu próprio "oi" e também encerrou a conexão digitando "sair".

2)Se o número de clientes instanciados for muito elevado, o consumo de memória e processamento da máquina do servidor aumentará drasticamente, o que pode causar lentidão severa ou travamentos.
Sim, existe um limite para a quantidade de clientes nessa aplicação. O limite máximo exato de clientes simultâneos será sempre restrito ao limite de Threads que o Sistema Operacional (SO) consegue gerenciar. Quando o SO não puder mais criar novas Threads, o servidor não conseguirá aceitar novos clientes.

3) Ao iniciar apenas a classe ClienteBatepapo.java, o programa tenta instanciar um novo Socket conectando-se ao endereço IP e porta do servidor (127.0.0.1:3307). Como a classe ServidorBatepapo.java não está em execução, não existe nenhum serviço "escutando" na porta 3307. O sistema operacional recusa a conexão, lançando uma java.net.ConnectException. Essa exceção (que herda de IOException) é capturada pelo bloco try-catch no método main do cliente, que imprime a mensagem de erro e encerra a aplicação. No console do cliente aparecerá:*v*v*v* CONSOLE DO CLIENTE *v*v*v*Erro ao iniciar o cliente: Connection refused: connectCliente finalizado!

4)A classe ServidorBatepapo.java inicia criando um ServerSocket vinculado à porta 3307 local. Em seguida, entra no método clientConnectionLoop(), que contém um laço infinito (while(true)). Dentro desse laço, o servidor executa o método serverSocket.accept(). Este é um método bloqueante: ele trava o fluxo de execução da Thread principal do servidor até que uma requisição de conexão de um cliente chegue. Como nenhum cliente foi iniciado, o servidor ficará permanentemente "escutando" a porta, sem avançar para a próxima linha de código. No console do servidor aparecerá:*v*v*v* CONSOLE DO SERVIDOR *v*v*v*Servidor iniciado na porta: 3307. Aguardando conexao de um cliente! (O console fica travado/aguardando neste ponto indefinidamente).

5) Quando o cliente é executado, ele estabelece uma conexão com o servidor, o que desbloqueia o método accept() e gera um novo socket exclusivo para essa comunicação. Imediatamente, o servidor adiciona esse cliente a uma lista (clients.add) e inicia uma nova Thread (clientMessageLoop) dedicada apenas a escutar suas mensagens, permitindo que a Thread principal retorne ao laço while(true) e aguarde novas conexões no accept(). Ao digitar uma mensagem, o cliente a envia por meio de saida.println(msg) e a Thread dedicada no servidor a captura com clientSocket.getMessage(), exibindo-a no console. Em seguida, o servidor tenta retransmitir o texto para os demais usuários usando o método sendMsgToAll, mas, como há apenas um cliente conectado, a verificação !sender.equals(clientSocket) resulta em falso e evita que a mensagem volte ao remetente. Por fim, quando o usuário digita "sair", o laço do-while do cliente é encerrado e seu bloco finally fecha os fluxos de dados e o socket, finalizando o programa. Do lado do servidor, o recebimento da palavra "sair" valida a condição if("sair".equalsIgnoreCase(msg)), acionando um return que encerra a Thread dedicada, fecha o socket correspondente no bloco finally e mantém o servidor principal ativo na porta 3307.

6) Neste cenário, a aplicação se mantém estável e aguardando novas ações de ambos os lados. No servidor, a Thread principal retorna ao laço while(true) e fica bloqueada no método accept(), esperando silenciosamente por um segundo cliente. Paralelamente, a Thread dedicada ao Cliente 1 recebe a primeira mensagem, exibe-a no console do servidor e chama o método sendMsgToAll. Como não há outros usuários na lista, nenhuma retransmissão ocorre e a Thread volta a ficar bloqueada no getMessage(), aguardando o próximo envio. Enquanto isso, no Cliente 1, a Thread principal permanece parada no scanner.nextLine() esperando que o usuário digite algo, ao mesmo tempo em que a Thread secundária (run()) fica bloqueada no getMessage() aguardando dados do servidor, mantendo o cursor piscando na tela.

7) Esta etapa comprova o funcionamento pleno da arquitetura multicliente e da comunicação bidirecional. Quando o Cliente 2 se conecta, a Thread principal do servidor é liberada do accept(), aceita a nova conexão, adiciona o usuário à lista clients e cria uma segunda Thread exclusiva para ouvi-lo. Ao enviar a mensagem "Oi, cliente 2!", a Thread dedicada ao Cliente 1 no servidor captura o texto e aciona o sendMsgToAll, que percorre a lista de conectados e, ao validar pela condição !sender.equals(clientSocket) que o Cliente 2 não é o remetente, repassa a mensagem para ele. A Thread secundária do Cliente 2 recebe o conteúdo e o exibe na tela com o prefixo ->, demonstrando que o recebimento ocorre simultaneamente à espera por digitação na sua Thread principal. Quando o Cliente 2 responde, o mesmo fluxo acontece de forma invertida, mantendo todas as conexões ativas e o servidor pronto para aceitar um terceiro participante.

8) A adição de um terceiro cliente consolida o comportamento da lista encadeada e do reenvio em massa (broadcast). Quando a terceira instância é executada, a Thread principal do servidor libera o accept(), instancia o SocketCliente para o Cliente 3, adiciona-o à lista clients (que passa a ter tamanho 3) e inicia uma terceira Thread dedicada de escuta. Sempre que qualquer participante envia uma mensagem, sua respectiva Thread no servidor aciona o método sendMsgToAll. O iterador percorre os três clientes cadastrados e, devido à condicional if(!sender.equals(clientSocket)), retransmite o texto apenas para as duas conexões que não são a remetente. Em seguida, as Threads secundárias (run()) nos clientes receptores captam os dados e os exibem no console simultaneamente, sem interromper suas Threads principais que continuam aguardando novas digitações.

9) Ao digitar "sair" no Cliente 1, a variável msg quebra a condição do laço do-while do método messageLoop() e aciona o bloco finally, fechando os fluxos de dados e o respectivo socket no lado do cliente. Paralelamente, a string "sair" chega ao servidor e é capturada pela Thread dedicada ao Cliente 1 dentro do laço while((msg = clientSocket.getMessage()) != null). Isso valida a condicional if("sair".equalsIgnoreCase(msg)) e dispara o comando return, que aborta imediatamente o método clientMessageLoop e executa o bloco finally do servidor, chamando clientSocket.close() para encerrar a Thread de forma limpa e liberar memória. O mesmo fluxo ocorre isoladamente quando os Clientes 2 e 3 digitam "sair", enquanto o servidor principal permanece ativo e travado no accept(), totalmente imune ao encerramento das Threads secundárias.

10) Este cenário evidencia o conflito de alocação de porta (TCP Binding) em redes baseadas no protocolo TCP/IP, nas quais uma porta associada a um endereço IP só pode ser vinculada a um único processo por vez. Como a primeira instância do servidor já realizou o vínculo (bind) com a porta local 3307, a tentativa da segunda instância de executar a instrução serverSocket = new ServerSocket(PORT) é recusada pelo Sistema Operacional, resultando no lançamento de uma exceção do tipo java.net.BindException (subclasse de IOException). Essa falha é imediatamente capturada pelo bloco catch (IOException ex) do método main do segundo servidor, que exibe a mensagem informando que o endereço já está em uso e encerra o programa. Enquanto isso, a primeira instância permanece intacta e operando normalmente, pois o bloqueio ocorreu diretamente no nível da API de Sockets e do Sistema Operacional, sem interferir no processo já estabelecido.
